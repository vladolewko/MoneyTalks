# Технічне завдання та опис продукту MoneyTalks

Документ фіксує **ціль продукту**, **функціональні вимоги**, **нефункціональні вимоги** та **етапи розвитку**. Версія: **0.3** (узгоджено з поточним MVP у репозиторії).

---

## 1. Назва та призначення

**MoneyTalks** — мобільний застосунок для **обліку доходів і витрат**, перегляду **статистики та графіків**, з перспективою **автоматизації вводу** (зокрема через **розпізнавання чеків** за допомогою AI).

**Цільова аудиторія**: користувачі, які хочуть швидко фіксувати грошові рухи та бачити картину за періодами без складної бухгалтерії.

---

## 2. Цілі та метрики успіху

| Ціль | Опис | Індикатор (на етапі зрілості) |
|------|------|--------------------------------|
| Швидкий ввід | Додати транзакцію за ≤ 30 секунд | UX-тести, аналітика подій |
| Довіра до даних | Дані не губляться при перевстановленні застосунку (сервер як джерело правди) | Резервне копіювання БД, моніторинг помилок API |
| Зрозуміла аналітика | Користувач бачить баланс і динаміку без навчання | Retention, опитування |

---

## 3. Область продукту (scope)

### 3.1. У межах продукту (in scope)

- Облік **доходів** і **витрат** (сума, валюта, дата, категорія, нотатка).
- **Список операцій** з оновленням з сервера.
- **Агрегована статистика** (суми за типами, розбивка по місяцях для графіків).
- **Реєстрація / вхід**, орієнтовані на мінімальний бар’єр: **ідентифікатор пристрою** + серверний обліковий запис і **API-токен** (Sanctum).
- **Мінімалістичний UI**: темна тема, читабельна типографіка, мало відволікаючих елементів.

### 3.2. Поза межами поточного MVP (out of scope зараз, in scope майбутнього)

- Повноцінна **email/SMS-верифікація**, соціальний логін, відновлення пароля «як у банку».
- **Мультивалютний** обмін по курсу ЦБ / комерційні курси.
- **Спільні гаманці**, ролі в сім’ї/команді, експорт для податкової.
- **Офлайн-режим** з надійною синхронізацією конфліктів.
- **Нативна інтеграція з банками** (PSD2 тощо) — окреме юридичне та технічне ТЗ.

## 4. Функціональні вимоги

### 4.1. Обліковий запис і безпека

| ID | Вимога | Пріоритет | Статус MVP |
|----|--------|-----------|--------------|
| F-AUTH-1 | Клієнт генерує стабільний `device_uuid` і зберігає його локально | Must | Реалізовано |
| F-AUTH-2 | Сервер приймає `device_uuid`, створює або знаходить користувача, видає Bearer-токен | Must | Реалізовано |
| F-AUTH-3 | Токен зберігається на пристрої; запити до API виконуються з заголовком `Authorization` | Must | Реалізовано |

| F-AUTH-5 | Опційне підсилення: прив’язка до Apple/Google акаунта без втрати історії | Could | Беклог |

## 5. API (контракт на високому рівні)

Базовий префікс: **`/api`**. Формат: **JSON**. Авторизація: **`Authorization: Bearer <token>`** для захищених маршрутів.

| Метод | Шлях | Призначення |
|--------|------|-------------|
| POST | `/auth/register` | Реєстрація користувача (Email/Password) |
| POST | `/auth/login` | Вхід та отримання токена |
| POST | `/auth/logout` | Вихід (анулювання токена) |
| GET | `/user` | Поточний користувач |
| PATCH | `/profile` | Оновлення профілю (наприклад, ім'я) |
| GET | `/transactions` | Список транзакцій (пагінація, фільтри) |
| POST | `/transactions` | Створення |
| PUT | `/transactions/{id}` | Оновлення |
| DELETE | `/transactions/{id}` | Видалення |
| GET | `/stats/summary` | Підсумки та помісячні дані |

**Детальний опис** (приклади запитів/відповідей, схеми тіла, OpenAPI): згенерована документація **Scribe** у каталозі `backend/public/docs/`.

## 6. Нефункціональні вимоги

| Категорія | Вимога |
|-----------|--------|
| Продуктивність | Основні read/write операції p95 < 500 ms при нормальному навантаженні MVP. |
| Доступність | UI з контрастними кольорами, підтримка динамічного типу (за можливості RN). |
| Безпека | HTTPS у продакшені; захист від mass assignment; rate limiting на `/auth/*` (прод). |
| Надійність | Регулярні бекапи БД; health-check (`/up` у Laravel). |
| Спостережуваність | Структуровані логи, кореляційний ID запиту (етап зрілості). |
| Документація API | Scribe-артефакти в `backend/public/docs/` оновлюються одночасно зі змінами маршрутів. |

---

## 7. Модель даних (логічна)

- **User**: користувач; email та пароль; стандартні поля Laravel.
- **Transaction**: зв’язок з `user_id`, тип, сума, валюта, категорія, нотатка, момент події.
- **personal_access_tokens** (Sanctum): видані токени доступу.

---

## 8. Клієнтський застосунок (вимоги до UX)

- **Навігація**: Tab-based через `expo-router` (Dashboard, Add Transaction, Statistics, All Transactions).
- **Темна тема**: динамічна підтримка світлого/темного режимів.
- **Pull-to-refresh** для синхронізації.
- **Push-сповіщення**: локальне сповіщення.
- **Демо-сценарій**: запуск `DemoUserSeeder` на бекенді для миттєвого тестування.

## 10. Ризики та припущення

- **Локальний запуск Expo**: вимагає правильного налаштування `.env` та іноді очищення кешу (`npx expo start --clear`).
- **Push-сповіщення в Expo Go**: на SDK 53+ не працюють віддалені сповіщення (лише локальні або потрібен custom dev client).

---

## 11. Глосарій

- **Транзакція** — один запис доходу або витрати.
- **Bearer-токен** — секрет доступу до API, виданий Sanctum.
